# T-D16a — Multi-user migration `0012_multi_user.sql`

- **Phase**: 1 — App Prerequisites
- **Parallel-safe**: no — must land first within Phase 1 auth/user chain
- **Depends on**: nothing
- **Blocks**: T-D02, T-D16, T-D17, T-D18, T-D19 (any work that reads the new `users` columns or the de-sentineled `user_id` columns)
- **References**: [ADR-0061](../../../adr/0061-v3-multi-user-admin-bootstrap-and-data-isolation.md) §2

## Context

ADR-0005 scaffolded a nullable `user_id DEFAULT 1` column on every user-owned table and seeded a single `users(id=1, name='default')` row. ADR-0061 activates that scaffold: `users` grows into a real identity table with email + bcrypt password hash + role flag; the `DEFAULT 1` sentinel is dropped so new rows must declare `user_id` explicitly.

Existing data must be preserved — the operator migrating from v2 keeps all transactions, accounts, categories, etc. as the bootstrapped admin's own history (via the `user_id = 1` rows that already exist).

## Deliverables

1. **Migration `migrations/0012_multi_user.sql`**:
   - `ALTER TABLE users ADD COLUMN email TEXT;`
   - `ALTER TABLE users ADD COLUMN password_hash TEXT;`
   - `ALTER TABLE users ADD COLUMN is_admin INTEGER NOT NULL DEFAULT 0 CHECK (is_admin IN (0, 1));`
   - `ALTER TABLE users ADD COLUMN must_change_password INTEGER NOT NULL DEFAULT 0 CHECK (must_change_password IN (0, 1));`
   - `ALTER TABLE users ADD COLUMN updated_at TIMESTAMP NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'));`
   - `ALTER TABLE users ADD COLUMN deleted_at TIMESTAMP;`
   - `CREATE UNIQUE INDEX ux_users_email_live ON users (lower(email)) WHERE deleted_at IS NULL;`
   - For each of `accounts`, `categories`, `transactions`, `planned_transactions`, `recurring_rules`, `budget_defaults`, `budget_recurring_overrides`, `budget_one_off_overrides`, `user_preferences`: rebuild via `CREATE TABLE _new (...) → INSERT INTO _new SELECT ... → DROP TABLE old → ALTER TABLE _new RENAME TO old`, where the new table definition omits `DEFAULT 1` on `user_id` and keeps all other constraints, indices, and foreign keys. Re-create every index, trigger, and unique constraint listed in `migrations/0002_core_schema.sql` for the affected table.
   - `ALTER TABLE audit_log ADD COLUMN actor_user_id INTEGER REFERENCES users (id);` (nullable; NULL for system-bootstrap and historical rows). Additive to the request-context columns from T-D14.
2. **Down migration** (companion `migrations/down/0012_multi_user_down.sql`) that reverses the schema — purely for CI's "forward then backward" smoke; not expected to be run in production.
3. **Migration runner**: no change required if the existing runner picks up numeric prefixes in `migrations/`. Add an assertion to the runner's integration test that `0012` applies cleanly on top of a v2 schema snapshot.
4. **Snapshot fixture** `tests/fixtures/v2_schema_snapshot.sql` (one-time, generated by `scripts/dump_schema.sh` against the current `main`): the baseline the migration test runs against.

## Acceptance criteria

- `pytest tests/integration/db/test_migrations.py::test_0012_applies_to_v2_snapshot` passes. The test:
  - Creates a fresh SQLite file.
  - Loads `tests/fixtures/v2_schema_snapshot.sql` + a handful of seed rows (one account, two transactions, two categories) under `user_id = 1`.
  - Applies migration `0012`.
  - Asserts: all seed rows survive; `users` row (id=1) is present with `email IS NULL` + `is_admin = 0` + `deleted_at IS NULL` (T-D19 promotes it); `user_id` column on every rebuilt table has no `DEFAULT 1`; `ux_users_email_live` exists; `audit_log.actor_user_id` column exists.
- `pytest tests/integration/db/test_migrations.py::test_0012_down_reverses` passes. The test applies `0012` then runs the down migration and asserts the schema matches the snapshot.
- `just lint` (sqlfluff) is clean against both migration files.
- `just typecheck` passes (no type impact; migrations are pure SQL).
